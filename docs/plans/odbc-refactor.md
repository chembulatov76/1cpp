# ODBCRecordset (1С++): оценка и план рефакторинга

## Контекст

Пользователь спросил, стоит ли рефакторить ODBC-часть 1С++, чтобы поднять надёжность и производительность. В Shininvest `ODBCRecordset` используется повсюду: `ВыполнитьИнструкцию` встречается около 1000 раз (956 из них через одну переменную `RS`), `ВыполнитьСкалярный` около 150, `УложитьСписокОбъектов` 81, `УстановитьТекстовыйПараметр` около 3100. Типизация `$Справочник`/`$Документ` встречается около 2500 раз. Подготовленные запросы (`Подготовить`) используются 6 раз, `РежимRPC` 13, а `УстРазмерМножестваСтрок`, `ВыполнитьSQL_ИзТЗ` и `ВыполнитьXML` не используются вовсе.

Что важно знать заранее:
- **В проде стоит `1cpp.dll` 3.2.4.1** (2013, 2 068 480 б, SHA256 `669967…74EF`). В этом репозитории исходники **3.2.4.3** и их сборка на ICL (`dist/1CPP.dll`, 2 043 904 б). Поэтому любая пересборка меняет весь 1С++ целиком, а не только ODBC.
- Тестов ODBC нет: в `Testing/UnitTests/ODBC` лежат три заглушки.
- Код ODBC: `Source/ODBC/Odbccore.cpp` (ядро, 4,1 тыс. строк, основано на обёртке C. Antollini 2001 года), `1CPP_ODBCRecordSet.cpp` (методы 1С, 2,9 тыс.), `MetaNameParser.cpp` (препроцессор `$`, `:`, `?`, ВТ, 3,3 тыс.), `SQL/MetaDataWork.cpp` (перевод 1С ↔ строки БД).

## Оценка

Основной путь — `ВыполнитьИнструкцию` и `ВыполнитьСкалярный` на родном подключении 1С с типизацией `$` — годами работает в проде, и это видно по коду. Но код в стиле C с MFC. Владение памятью идёт через `union` указателей, RAII нет. Ошибки передаются как `BOOL` вместе со строкой. Встречаются магические смещения в объекты 1С и ассемблерная вставка. Циклы заполнения скопированы по шесть раз (три приёмника × «с массивом строк» и «без»), много закомментированного мёртвого кода. На редких путях лежат реальные дефекты: от тихой порчи данных до падения 1С.

### Производительность: где выигрыш реален

Компонента — тонкий слой. Время в основном уходит на SQL Server и на создание значений 1С (`CValue`, `AddRow`). «Значительно» быстрее станет только в отдельных местах:

1. **`УложитьСписокОбъектов`** вставляет по строке: при списке в 5000 элементов это 5000 обращений к серверу. Пакетная вставка через массив параметров (`SQL_ATTR_PARAMSET_SIZE`, механизм уже есть в `AllocateRowsetForParams`) даёт выигрыш в десятки раз на больших списках.
2. **Компиляция планов на SQL Server — во многом уже закрыта сервером.** Текстовые параметры подставляются литералами, но у базы `Shininvest` и на деве (`localhost`), и на проде (`SQLSERVER8`) включена принудительная параметризация (`is_parameterization_forced = 1`, проверено чтением 2026-10-12), а также RCSI. Сервер сам заменяет литералы параметрами и переиспользует планы. `РежимRPC` по умолчанию не нужен (к тому же в нём `#временные` таблицы живут только внутри вызова). Отдельно смотреть стоит только запросы, которые принудительная параметризация не берёт.
3. **Выборка в ТЗ.** Блочная выборка (`SQL_ATTR_ROW_ARRAY_SIZE`) автоматически, когда в выборке нет длинных полей, сокращает число вызовов ODBC в сотни раз. Ожидаемый выигрыш на больших выборках — около 10–30 % от доли компоненты. Нужен замер.
4. Мелочь: новый `HSTMT` на каждый запрос.

### Типизация `$Справочник`/`$Документ` и выгрузка в ТЗ (вопрос пользователя от 2026-10-12)

Что сейчас происходит на каждую ячейку `[Товар $Справочник.Номенклатура]` в `ВыполнитьИнструкцию` → ТЗ (`Odbccore.cpp:2482-2540`, `MetaDataWork.cpp:2229-2262`, `1CPP_ODBCRecordSet.cpp:397-443`):
- 2–3 вызова `CType::GetTypeCode/GetTypeID`. Это импорт из `BkEnd.dll`, а не встроенный код.
- Временная `CString` из буфера (выделение памяти, `strlen`, копирование, освобождение), хотя данные уже лежат в буфере ODBC.
- `CValue::SetType` → `strtol(…,36)` → конструкторы `CDBSign` и `CObjID` → `CValue::SetObjID` с копией `CObjID`. Ещё 4–5 импортных вызовов.
- `AddRow` копирует каждое 84-байтное `CValue` (число, строка, дата, контекст и `ObjID` разом) в хранилище колонки. Значение собирается дважды: во временное `CValue`, потом в ТЗ.
- Обновление ТЗ при загрузке не отключается. В 1С++ есть готовый приём `CDerivedVT::m_bEnableRefresh = FALSE` (`VTExtended.cpp:1695`, `VLResultLoader.cpp:119`), но `ВыполнитьИнструкцию` его не использует. Если ТЗ показана на форме, каждая строка может дёргать обновление элемента.
- Особые типы дороже: `$ВидДокумента…`/`$ВидСправочника…` ищут объект в метаданных и создают строку на каждой ячейке (`Odbccore.cpp:2384-2411`, `2542-2569`). `$Документ`/`$Субконто` с колонкой `_вид` каждый раз вызывают `GetDataSourceType`, `GetBuhDef` и `GetSbKindDefs()->GetItem` (`2570-2594`).

Вывод по коду: гипотеза правдоподобна. На ячейку приходится около 10 вызовов в DLL 1С, одна строка в куче и полная копия значения. Катастрофы по коду не видно: при пяти типизированных колонках ожидаю десятки процентов от времени выгрузки, а не разы. В разы может дать отключение обновления у ТЗ на форме. Всё это оценка без замера.

Уровни «записи напрямую»:
1. **Без хаков.** Конвертер на колонку выбирается один раз при открытии. Base36 разбирается прямо из буфера ODBC, без `CString`. Тип временного `CValue` ставится один раз на колонку. Метаданные для `$Вид…` и `_вид` кэшируются на колонку. На время загрузки отключается обновление ТЗ. Риск низкий.
2. **Прямая запись в поля `CValue`.** Раскладка известна из `1CHEADERS/bkend.h:5273` (`m_ObjID`, `m_mdid`, `ValTypeID`), 1С++ уже читает их напрямую (`VTExt/CVCompare.h:97-105`). Тип ставится штатно один раз, дальше на каждой строке пишутся только `m_ObjID.ObjID` и `DBSign`. Риск низкий или средний.
3. **Прямая запись в хранилище колонок ТЗ** в обход `AddRow` и временного `CValue`. `CVTColumn` — непрозрачные 160 байт с массивом своего типа на колонку (`GetArrayType`). Нужен разбор `BkEnd.dll`, плюс ключи и индексы ТЗ (`EmptyKeys`/`FillKeys`). Ошибка обернётся порчей памяти и падением 1С на проде. Промежуточный путь — штатные экспортируемые `CValueTable::SetRowCount`, `CVTColumn::AddItems` и `CVTColumn::Set`: вставка блоком, затем запись по ячейке. Уровень 3 только по итогам замера и если промежуточного пути не хватит.

Быстрый путь включается переключателем в рантайме: `RS` или глобальная настройка, чтобы при сбое вернуться на старый путь без замены DLL.

Прецедент глубоких хаков ради скорости в 1С++ уже есть: `TurboBL` подменяет таблицы виртуальных методов у ТЗ, справочников и документов. В Shininvest он включён (`Настройки.Установить("EnableTurboBL", 1)`, глобальный модуль, строка 3094).

**Выводы.**

- **Гипотеза о дорогой типизации не подтвердилась.** Типизация `$Справочник`/`$Перечисление` стоит меньше погрешности замера, `$Документ` с `_вид` — 0,03 мкс на ячейку. Весь путь ODBC → `CValue` → ТЗ — около 0,2 с на 1,3 млн ячеек. Уровни 1–3 «записи напрямую» ради скорости не нужны и отложены.
- Блочная выборка (массив строк) выигрыша не даёт: сервер локальный, драйвер и так быстрый.
- **Настоящее узкое место — заполнение ТЗ, показанной на форме**: 340 мкс на строку. `ВыполнитьИнструкцию` добавляет строки с включённым обновлением ТЗ, `m_bEnableRefresh` не отключается (`1CPP_ODBCRecordSet.cpp:379-443`). В Shininvest вызовов `RS.ВыполнитьИнструкцию(Текст, ТЗ)` с уже существующей ТЗ — 424, часть из них заполняет ТЗ формы.

- Цена прямого заполнения почти постоянна на строку: тормоз заметен уже на тысяче строк (~0,3 с), на 10 тысячах — 2,6 с.
- V10 заполняет ТЗ формы тем же `AddRow`, что и `ВыполнитьИнструкцию`, но с `CDerivedVT::m_bEnableRefresh = FALSE` (загрузчик 1С++, `VLResultLoader.cpp:119`). Выходит 0,39 с вместо 34 с. **Приём со смещением `0x3C` работает на релизе 1С 7.70.025** (заголовки 1С++ размечены для R27): исправление в компоненте проверено на деле.
- **Заморозка окна не помогает.** Прямое заполнение ТЗ формы под `РасширениеФормы.ЗапретитьОбновлениеОкна` (`V11м`, 10 000 строк) — 3 104 мс против 2 624 мс без заморозки (отчёт `zamer_report_zamorozka.txt`). Время уходит не на отрисовку, а на уведомления ТЗ и элемента таблицы о каждой строке. Формы Shininvest с заморозкой окна (`ВБ_ЗаданияДляПодборки`, `УП_ОбработкаЗаявок`) при заполнении ТЗ формы через RS платят полную цену. Помогают только отключение `m_bEnableRefresh` (V10) или временная ТЗ + `Выгрузить` (V9).

**Новый порядок работ по производительности.**

1. **Главное — `ВыполнитьИнструкцию` в существующую ТЗ.** На время `Clear`/`AddColumn`/`AddRow` выставлять `m_bEnableRefresh = FALSE` и в конце сделать одно обновление: как `VTExtended.cpp:1693-1778` и `VLResultLoader.cpp:111-146`, со стражем на исключение. 4. `УложитьСписокОбъектов` (пакетная вставка) — отдельный замер, если понадобится.

## Сторонний разбор (ChatGPT, 2026-10-12) против замеров

Пользователь показал разбор тех же исходников. Что подтверждается, а что нет:

- **«Главное место — `ПолучитьРезультатыВ_ТЗ`: на каждую ячейку `SetPropVal` через `CBLContext`».** Про сам метод верно. Но в Shininvest он не используется (0 вызовов), основной путь — `ВыполнитьИнструкцию` (3 634 упоминания).
- **«Закомментированная прямая запись в `CValueTable` — важная находка».** Прямая запись уже сделана в `ВыполнитьИнструкцию`: `pVT->AddRow` (`1CPP_ODBCRecordSet.cpp:397-443`). Её цена измерена: 0,17 мкс на ячейку вместе с выборкой ODBC, 100 тыс. × 13 — 0,22 с.
- **«Прямое пакетное заполнение `CValueTable` — высокий потенциал».** Профилем не подтверждается. Код `1cpp.dll` — 4,5 % CPU выгрузки, остальное — значения 1С (`BkEnd`), куча, драйвер. Потолок выигрыша — ~0,05–0,1 с на 100 тыс. строк, при риске порчи памяти.
- **«Цена превращения ссылок SQL в объекты 1С».** Измерено: почти ноль (V2−V1 ≈ 0, `$Документ` — 0,03 мкс на ячейку).
- **«Переиспользование SQL-запросов».** На деве и проде включена принудительная параметризация, сервер и так переиспользует планы.

**Решение.** На вопрос «как исправляем» пользователь ответил «Оба: сначала компонента».

**Устройство** (`fix1c/`, VC6 + SDK 1С `C:\Install\vc6\1c-sdk`, схема Орефкова как у `Json1C`):

- Класс 1С `ИсправлениеODBC` (`OdbcFix`). Методы:
  - `Включить()`, `Выключить()`, `Включено()`;
  - `Версия()`, `Сведения()`;
  - `ПроверитьОбъект(RS)` — 1, если объект идёт через исправление;
  - `ОбновлениеВключено(ТЗ)` — флаг обновления ТЗ, для тестов.

  Свойство `ТекстОшибки`. Методы не бросают исключений в 1С.
- `Включить()`:
  1. Создаёт временный `ODBCRecordset`, берёт его таблицу виртуальных методов (часть `CBLContext`, общая для всех `ODBCRecordset`).
  2. Проверяет, что таблица и методы `CallAsProc`/`CallAsFunc`/`FindMethod`/`FindProp` лежат в образе `1cpp.dll`, а место `CallAsFunc` = 32 сходится с тем, как его разложил компилятор (разбор vcall-thunk). Нумерация мест — как у `TurboBL`: `FindProp` 19, `FindMethod` 26.
  3. Записывает в место 32 свою обёртку (`VirtualProtect`, `PAGE_EXECUTE_READWRITE`).
  4. Номер метода `ВыполнитьИнструкцию` берёт через `FindMethod("ExecuteStatement")`.
- Обёртка: если вызвана не `ВыполнитьИнструкцию` или приёмник не обычная ТЗ (`CValueTableContext`), вызывается исходный метод без изменений. Иначе:
  1. `CValueTable::m_bEnableRefresh` (смещение `0x3C`, есть в SDK) ставится в `FALSE`;
  2. вызывается исходный метод;
  3. флаг возвращается, делается одно обновление (`NewRow` + `DeleteRow`, как 1С++).

  Исключение 1С (`CBLRuntimeException`, C++) или аппаратное (`/EHa`) возвращает флаг и уходит в 1С без изменений. Если флаг уже выключен кем-то, обёртка его не трогает.
- `Выключить()` возвращает исходный адрес. При выгрузке компоненты (`DoneAddin`) исходный адрес возвращается автоматически.
